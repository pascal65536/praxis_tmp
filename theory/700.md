
# Что такое REST

**REST (Representational State Transfer — «передача репрезентативного состояния»)** — архитектурный стиль взаимодействия клиента и сервера через HTTP, описанный Роем Филдингом в 2000 году.

Три ключевых уточнения:

1. **REST — не протокол и не стандарт.** Это набор архитектурных ограничений. Веб-сервис, соблюдающий их, называют **RESTful**.
2. REST **полностью построен на HTTP**: когда вы вводите адрес в браузере, браузер выполняет запрос `GET` к ресурсу на сервере.
3. Клиент и сервер **не зависят от языка программирования**: клиент на Python и сервер на Java общаются, если оба говорят по HTTP.

### Ресурсы и URI

Центральная абстракция REST — **ресурс**: всё, чему можно дать имя. Пользователь, задача, заказ, город, фотография, даже результат вычисления. Каждый ресурс имеет **уникальный идентификатор — URI**:

```text
https://api.example.com/users
# коллекция пользователей

https://api.example.com/users/123 
# конкретный пользователь номер 123

https://wttr.in/Красноярск
# ресурс «погода в Красноярске»
```

Мышление при проектировании REST API состоит из двух шагов:

1. определить, какие **ресурсы** вы открываете внешнему миру;
2. оперировать **глаголами, которые уже определены в HTTP** (GET, POST, PUT, DELETE).

# 6 принципов REST

| Принцип | Суть |
|---------|------|
| **1. Клиент–сервер** | Клиент отвечает за интерфейс и взаимодействие с пользователем; сервер — за данные, бизнес-логику и обработку запросов. Стороны развиваются независимо: можно менять мобильное приложение, не трогая сервер, и наоборот. |
| **2. Отсутствие состояния (Stateless)** | Каждый запрос содержит **всю** информацию для своей обработки. Сервер не хранит контекст «диалога» с клиентом между запросами. Если нужна авторизация — токен присылается **с каждым запросом**. Плюс: любой запрос можно обработать на любой копии сервера — масштабирование тривиально. Минус: сообщения становятся крупнее — поэтому данные передают в компактном JSON. |
| **3. Кэшируемость (Cacheability)** | Ответы помечаются как кэшируемые или нет (`Cache-Control`, `ETag`). Повторный запрос может быть обслужен вообще без сервера. Это один из главных секретов масштаба Веба: CDN и браузерные кэши снимают основную нагрузку. |
| **4. Единый интерфейс (Uniform Interface)** | Идентификация ресурсов через URI; манипуляция ресурсами через их представления (JSON); самодостаточные сообщения (всё нужное — в запросе); HATEOAS — ответы содержат ссылки на связанные ресурсы, клиент «ходит» по API как по веб-страницам. |
| **5. Слоистая система (Layered System)** | Между клиентом и сервером могут быть промежуточные слои: прокси, шлюзы, балансировщики, CDN. Клиент не знает, общается ли он с конечным сервером. Это даёт гибкость и безопасность. |
| **6. Код по требованию (Code on Demand)** | Единственное **необязательное** ограничение: сервер может передавать клиенту исполняемый код (как JavaScript передаётся браузеру). |

# HTTP в деталях

## Структура запроса

```bash
POST /users HTTP/1.1          ← строка запроса: метод + URI + версия
Host: api.example.com          ┐
Content-Type: application/json │ заголовки (headers)
Authorization: Bearer …        ┘
                               ← пустая строка
{"name": "Мария"}              ← тело (body, необязательно)
```

Элементы:

- **Endpoint** — адрес запроса; у ресурса может быть несколько эндпоинтов;
- **Параметры пути** — `/users/123/posts`: 123 — часть пути;
- **Параметры запроса** — `/users?role=admin&sort=desc`: после `?`, пары `ключ=значение`, соединяются `&`;
- **Заголовки** — формат данных, аутентификация, версия протокола; в пути не видны;
- **Тело** — данные для обработки, обычно JSON.

## Структура ответа

```bash
HTTP/1.1 201 Created           ← строка состояния: код + пояснение
Content-Type: application/json  ┐
Location: /users/124            ┘ заголовки
{"id": 124, "name": "Мария"}    ← тело ответа (может быть пустым)
```

## Методы HTTP и CRUD

| Метод | CRUD | Назначение | Идемпотентность |
|-------|------|-----------|-----------------|
| GET | Read | Чтение ресурса или коллекции | Да |
| POST | Create | Создание нового ресурса | Нет |
| PUT | Update | Полная замена ресурса | Да |
| PATCH | Update | Частичное обновление (только переданные поля) | Нет |
| DELETE | Delete | Удаление ресурса | Да |
| HEAD | — | Заголовки ответа без тела | Да |
| OPTIONS | — | Какие методы доступны для ресурса | Да |

**Идемпотентность** — повторный одинаковый запрос даёт тот же результат, что и первый. Это не «пустое» свойство, а практическая необходимость: сети ненадёжны. Клиент, не дождавшись ответа на PUT, **вправе безопасно повторить** его — дубля не будет. А вот повторный POST создаст вторую запись. DELETE идемпотентен по смыслу «удалено»: второй DELETE просто получит 404.

Карта CRUD на примере задач:

```bash
GET    /tasks         список задач
POST   /tasks         создать задачу
GET    /tasks/42      задача с id=42
PUT    /tasks/42      заменить задачу целиком
PATCH  /tasks/42      изменить часть полей
DELETE /tasks/42      удалить задачу
```

## Коды статусов

Трёхзначное число. Первая цифра — класс:

| Класс | Значение | Примеры |
|-------|----------|---------|
| 1xx | Информационные | 100 Continue |
| 2xx | Успех | **200 OK** — чтение/обновление; **201 Created** — ресурс создан; **204 No Content** — успех без тела |
| 3xx | Перенаправление | 301 — перемещён навсегда; 304 — не изменилось (возьми из кэша); 307 — временно |
| 4xx | Ошибка клиента | **400 Bad Request**; 401 Unauthorized (нет аутентификации); 403 Forbidden; **404 Not Found**; **422 Unprocessable Entity**; 429 Too Many Requests |
| 5xx | Ошибка сервера | 500 Internal Server Error; 502 Bad Gateway; 503 Service Unavailable; 504 Timeout |

Тонкость: **400 vs 422**. 400 — запрос синтаксически некорректен: тело не JSON, отсутствует обязательное поле. 422 — синтаксис верен, но семантика неверна: поле `title` есть, но пустое; дата «30 февраля». Клиент может исправить данные и повторить.

## Пример из жизни: служба доставки

- `POST /orders` — передать новый заказ => **201**;
- `PUT /orders/123` — обновить данные заказа целиком => **200**;
- `PATCH /orders/123` — обновить только координаты курьера => **200**;
- `GET /orders/123?fields=status` — статус заказа => **200**;
- `DELETE /orders/123` — отменить заказ => **204**;
- повторный `DELETE /orders/123` => **404**: удалять уже нечего (идемпотентность).

# Пример взаимодействия

Запросим список задач:

```bash
curl -X GET https://api.example.com/tasks
```

Ответ (**200 OK**):

```json
[
  {"id": 1, "title": "Написать статью про REST API", "completed": false},
  {"id": 2, "title": "Выпить кофе", "completed": true}
]
```

Создадим задачу:

```bash
curl -X POST https://api.example.com/tasks \
     -H "Content-Type: application/json" \
     -d '{"title": "Проверить почту", "completed": false}'
```

Ответ (**201 Created**):

```json
{"id": 3, "title": "Проверить почту", "completed": false}
```

Обновим и удалим:

```bash
curl -X PUT https://api.example.com/tasks/3 \
     -H "Content-Type: application/json" \
     -d '{"completed": true}'                 # 200 OK

curl -X DELETE https://api.example.com/tasks/3   # 204 No Content
```

Полный цикл: 
1. Клиент формирует запрос (метод + URI + заголовки + тело)
2. Сервер идентифицирует ресурс и выполняет операцию
3. Возвращает код, заголовки и тело
4. Клиент интерпретирует ответ и либо показывает данные, либо реагирует на код 4xx/5xx.

## 7. Интересные API, за которые можно подёргать

Всё ниже — реальные, работающие сервисы. Часть доступна без регистрации, для части нужен бесплатный токен.

### 7.1. wttr.in — погода в терминале (без авторизации)

Сервис-легенда: погода как веб-страница, отдаваемая прямо в терминал.

```bash
curl wttr.in/Красноярск?lang=ru
curl wttr.in/Moscow?format=3        # короткий формат: "Moscow: 🌦 +7°C"
curl "wttr.in/?format=j1"           # ответ в JSON!
```

Обратите внимание: `?format=j1` — это обычный query-параметр, а значит wttr.in — фактически REST API, просто клиент у него — терминал.

# Яндекс.Статические карты — картинка карты по координатам 

API отдаёт **PNG-изображение** карты по URL-параметрам — `ll` (долгота,широта), `z` (зум), `l` (слой), `pt` (метка):

```bash
LAT=56.006154
LON=92.947142
curl "https://static-maps.yandex.ru/1.x/?ll=${LON},${LAT}&z=17&l=map&size=650,450&pt=${LON},${LAT},pm2rdm" -o yandex_map.png
```

Чистый REST: ресурс — «карта с параметрами», ответ — файл-картинка с кодом 200.

# DaData — нормализация адресов и ФИО

Российский сервис подсказок и «очистки» данных. Проверяет, что адрес существует, разбирает ФИО на фамилию/имя/отчество, исправляет регистр:

```bash
# Подсказка по адресу
curl -X POST -H "Content-Type: application/json" \
     -H "Accept: application/json" \
     -H "Authorization: Token ${TOKEN}" \
     -d '{"query": "Красноярск"}' \
     https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/postal_unit

# Стандартизация ФИО: "миша котюков михалыч" → фамилия Котюков, имя Михаил...
curl -X POST -H "Content-Type: application/json" \
     -H "Accept: application/json" \
     -H "Authorization: Token ${TOKEN}" \
     -H "X-Secret: ${SECRET}" \
     -d '["миша котюков михалыч"]' \
     https://cleaner.dadata.ru/api/v1/clean/name
```

Обратите внимание на **заголовки**: `Authorization: Token …` — классическая схема аутентификации через заголовок (принцип stateless: токен присылается с каждым запросом).

# Content Watch — проверка текста на уникальность

API принимает форму через `--data-urlencode` (тело запроса `application/x-www-form-urlencoded` — не только JSON бывает телом!):

```bash
TEXT='Полный пример кода для проверки текста...'

curl -X POST "https://content-watch.ru/public/api/" \
     -H "Accept: application/json" \
     --data-urlencode "key=${TOKEN_CW}" \
     --data-urlencode "test=1" \
     --data-urlencode "text=${TEXT}"
```

Урок: REST не значит «только JSON» — тело бывает и формой.

# jsonformatter.org — для ручной работы

Когда API вернул огромный JSON, неудобный для глаз, его удобно прогнать через валидатор/форматтер (jsonformatter.org): вставили — получили дерево с подсветкой. Полезный инструмент при отладке любых API.

### 7.7. Рекомендуемые упражнения

1. `curl httpbin.org/anything` с произвольными заголовками и параметрами — найдите их в ответе.
2. Получите карту своего города через static-maps и откройте PNG.
3. Запросите погоду wttr.in в формате `j1` и разберите структуру JSON.
4. Найдите в ответе GitHub поля `login`, `public_repos`, `followers` у любого известного разработчика.
5. Сравните: что вернёт сервер на `GET` к несуществующему ресурсу (`httpbin.org/status/404`).

## 8. Заключение

- **История:** от локальных библиотек (1960-е) через RPC, CORBA и XML-RPC к архитектурному стилю, который Филдинг сформулировал в 2000 году, а веб-индустрия массово приняла в 2000-х (Amazon, eBay, Flickr, Google Maps, Twitter).
- **Суть REST:** ресурсы с URI + стандартные методы HTTP + коды статусов + отсутствие состояния.
- **Шесть принципов** — это рецепт масштабируемости, выведенный из устройства самого Веба.
- **Практика:** любой, кто умеет отправлять HTTP-запрос, уже умеет пользоваться REST API — сегодня мы дергали погоду, карты, ФИО и факты о котах.

**Ключевая мысль:** REST — это не технология, а способ мышления: система — это набор ресурсов, а не набор функций.
